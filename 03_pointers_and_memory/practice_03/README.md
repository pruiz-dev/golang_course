# Практика: Охота за аллокациями (Escape Analysis)

## Задача (Бизнес-требование)
Твой техлид попросил тебя написать профилировщик, чтобы доказать команде, как возврат указателей из функции влияет на загрузку Garbage Collector-а. 
Тебе нужно написать две функции: одна должна возвращать данные безопасно (оставляя их на стеке), а другая должна заставить компилятор эвакуировать данные в Кучу.

## Критерии приемки (Acceptance Criteria)
1. Создай исполняемую программу (не забудь инициализировать модуль `practice_03`).
2. Напиши функцию `CreateValue()`, которая создает локальную переменную типа `int` (например, со значением 42) и возвращает **само значение**.
3. Напиши функцию `CreatePointer()`, которая создает локальную переменную типа `int` (например, 99) и возвращает **указатель** на нее.
4. В функции `main` вызови обе эти функции, чтобы компилятор не удалил их как неиспользуемые.
5. Запусти анализ утечек памяти в терминале с помощью команды `go build -gcflags="-m" .` (точка в конце обязательна).
6. **Критическое условие:** Скопируй вывод компилятора из консоли и вставь его в самый низ файла `main.go` в виде многострочного комментария (`/* ... */`).

## Архитектурные подсказки
- Обрати внимание на функции из стандартной библиотеки, например `fmt.Println()`. Когда ты запускаешь `go build -gcflags="-m"`, ты можешь заметить, что переменные, переданные в `Println`, тоже убегают в кучу. Это происходит потому, что `Println` принимает интерфейс `any` (пустой интерфейс), а конвертация в интерфейс всегда заставляет переменную "убегать" в кучу. Если хочешь чистого эксперимента — не используй `fmt` в этом задании, просто вызови свои функции и сохрани результат в пустые переменные `_ = CreateValue()`.

Напиши код, проведи анализ компилятора, вставь результат в комментарий и присылай на ревью!
