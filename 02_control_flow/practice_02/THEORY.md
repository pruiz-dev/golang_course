# Теория: Единственный цикл `for` и ловушки `range`

В Go решили отказаться от зоопарка циклов (нет `while`, нет `do-while`). Вместо этого есть только один универсальный цикл — `for`.

## 1. Классический цикл
Работает так же, как в C/Java: инициализация, условие, пост-действие.
```go
for i := 0; i < 5; i++ {
    fmt.Println(i)
}
```

## 2. Аналог `while`
Если убрать инициализацию и пост-действие, `for` превращается в `while`:
```go
for condition == true {
    // Делаем что-то
}
```
А если убрать вообще всё, получится бесконечный цикл `for { ... }`.

## 3. Магия `for range`
Самый частый способ перебора массивов, слайсов и мап — это конструкция `range`. Она всегда возвращает **два значения**:
1. Индекс (ключ)
2. Копию значения (элемент)

```go
nums := []int{10, 20, 30}
for index, value := range nums {
    fmt.Printf("Индекс: %d, Значение: %d\n", index, value)
}
```
Если тебе нужен только индекс, второе значение можно опустить: `for i := range nums`.
Если тебе нужно только значение, индекс нужно явно проигнорировать (через blank identifier `_`): `for _, v := range nums`.

## 4. Ловушка №1: Изменение по копии (Value semantic)
Это самая частая ошибка новичков. Переменная `value` в конструкции `for _, value := range ...` — это **копия** реального элемента из массива. 

Если ты попытаешься изменить `value` внутри цикла, исходный массив **не изменится**:
```go
users := []string{"Alice", "Bob"}
for _, user := range users {
    user = "Hacked!" // Мы меняем только локальную копию переменной user
}
// Слайс users остался ["Alice", "Bob"]
```
**Как исправить?** Если нужно изменить оригинальные данные, обращайся к ним напрямую по индексу:
```go
for i := range users {
    users[i] = "Hacked!" // Теперь работает!
}
```

## 5. Легендарная Ловушка №2: Указатель на переменную цикла
До версии Go 1.22 цикл `for range` имел архитектурный изъян, который "убивал" продакшен-сервера.
Компилятор создавал переменную `value` **один раз** перед началом цикла, а затем просто перезаписывал её значение на каждой итерации.
Если разработчик пытался сохранить *адрес памяти* этой переменной (или запускал асинхронные горутины, ссылаясь на неё), то в итоге все сохраненные указатели смотрели на **одну и ту же ячейку памяти**, в которой оставалось значение из **самой последней итерации**.

*Начиная с Go 1.22, эту логику исправили (теперь переменная пересоздается на каждой итерации)*, но на собеседованиях этот вопрос до сих пор является лакмусовой бумажкой на понимание механики работы памяти и истории языка.
