# Теория: Операция нарезки (Slicing) и Утечки памяти

Мы переходим к самой коварной части работы со слайсами в Go — к операции нарезки, или "слайсингу". Именно здесь программисты, пришедшие из других языков, совершают фатальные ошибки, роняющие сервера в production из-за `Out of Memory` (нехватки памяти).

## 1. Синтаксис нарезки (Slicing)
В Go ты можешь создать новый слайс из уже существующего слайса (или массива), взяв только нужный тебе кусок. Для этого используется синтаксис `[low:high]`.

```go
loot := []string{"Золото", "Кинжал", "Броня", "Свиток", "Зелье"}

// Нарезаем с индекса 1 по индекс 3 (элемент с индексом 3 не включается!)
weapons := loot[1:3] // ["Кинжал", "Броня"]

// Сокращения:
firstTwo := loot[:2]   // С начала и до индекса 2
lastThree := loot[2:]  // С индекса 2 и до самого конца
all := loot[:]         // Полная копия заголовка
```

## 2. Что происходит под капотом при нарезке?
Самое главное правило, которое нужно выбить на камне:
**Нарезка (slicing) НИКОГДА не копирует данные базового массива!**

Когда ты делаешь `weapons := loot[1:3]`, под капотом происходит следующее:
1. Создается **новая 24-байтовая структура** `SliceHeader` для переменной `weapons`.
2. Её указатель `Data` начинает смотреть на ту же самую область памяти, где лежат элементы массива `loot`, но **со смещением** (указывает прямо на элемент "Кинжал").
3. Поле `Len` становится равным 2 (ведь мы взяли два элемента: 1 и 2).
4. Поле `Cap` вычисляется как (вместимость оригинального массива минус начальное смещение).

Оба слайса (`loot` и `weapons`) теперь смотрят на **один и тот же кусок оперативной памяти**. Изменив "Броню" в `weapons`, ты изменишь её и в `loot`.

## 3. Ловушка и Утечка памяти (Memory Leak)
Garbage Collector (сборщик мусора) в Go работает по простому принципу: *"Пока на кусок памяти ссылается хотя бы один активный указатель, эту память удалять нельзя"*.

Представь ситуацию:
1. Твой сервер скачал из сети гигантский файл на 1 Гигабайт (создан слайс `hugeFile := make([]byte, 1000000000)`).
2. Тебе нужны только первые 10 байт из этого файла, чтобы прочитать его заголовок.
3. Ты делаешь: `header := hugeFile[:10]`.
4. Функция завершается, переменная `hugeFile` уничтожается, но ты сохранил `header` куда-то в базу или глобальную переменную.

**Что произойдет?**
Ты думаешь, что сохранил только 10 байт и Гигабайт памяти сейчас очистится. 
Но `header` — это слайс! Его внутренний указатель `Data` всё еще крепко держит начало этого гигабайтного массива в памяти. Сборщик мусора смотрит на массив и видит: *"Ага, слайс `header` всё еще смотрит на начало этого массива, значит я не могу удалить весь массив!"*.

В итоге: крошечный слайс на 10 элементов **удерживает в оперативной памяти 1 Гигабайт мусора**. Это классическая утечка памяти в Go, известная как Slicing Trap.
