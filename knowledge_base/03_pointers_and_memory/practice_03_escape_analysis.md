# База Знаний: Стек, Куча и Escape Analysis

Этот документ покрывает продвинутые концепции распределения памяти в Go. Знание этих механизмов отличает Junior-разработчика от Middle+.

Вся оперативная память программы в Go делится на две основные зоны: Стек и Кучу.

## 1. Стек (Stack)
Стек — это сверхбыстрая, упорядоченная память. 
* У каждой горутины (потока) есть свой личный Стек.
* Когда вызывается функция, для ее локальных переменных выделяется "кадр" (фрейм) на стеке.
* **Главное преимущество:** Как только функция выполняет `return`, её кадр на стеке мгновенно уничтожается аппаратно (путем сдвига указателя). На это не тратятся ресурсы CPU. Это бесплатно и невероятно быстро.

## 2. Куча (Heap)
Куча — это общая "свалка" памяти для всего приложения.
* Выделение памяти здесь работает медленнее.
* **Главная проблема:** Память в куче не очищается сама. Этим занимается **Garbage Collector (GC, Сборщик мусора)**.
* GC периодически сканирует кучу, тратит циклы CPU и может останавливать программу (микро-фризы STW - Stop The World), чтобы удалить мусор.

> **Золотое правило Go:** Старайся держать максимум переменных на Стеке. Чем меньше аллокаций (выделений памяти) в Куче, тем реже просыпается Garbage Collector, и тем быстрее работает приложение.

## 3. Escape Analysis (Анализ "утечек" в кучу)
В языках вроде C++ программист сам решает (через `new`/`malloc`), куда положить данные. В Go это решает компилятор. Этот механизм называется **Escape Analysis**.

Компилятор анализирует код и задает вопрос: *"Нужна ли эта переменная кому-то после того, как функция, которая ее создала, завершит работу?"*
* Если **НЕТ** -> переменная остается на Стеке.
* Если **ДА** -> переменная "убегает" (escapes) в Кучу.

### Классический пример побега (Escaping)
Если функция создает локальную переменную и возвращает **указатель** на нее, компилятор видит, что после завершения функции указатель уйдет наружу. Если оставить переменную на стеке, стек уничтожится, и указатель будет смотреть в пустоту (Dangling pointer).
Поэтому компилятор принудительно эвакуирует эту переменную в Кучу.

### Пустой интерфейс (`any` / `interface{}`)
Любая передача переменной в функцию, принимающую пустой интерфейс (например, `fmt.Println(a)`), заставляет переменную "убегать" в кучу. Это происходит из-за особенностей внутреннего устройства интерфейсов в Go.

## 4. Как отследить Escape Analysis?
Go дает нам мощный инструмент для профилирования решений компилятора:
```bash
go build -gcflags="-m" .
```
Флаг `-m` (optimization decisions) выведет в консоль весь процесс анализа. 
* Строка `escapes to heap` означает, что переменная улетела в Кучу (нагрузив GC).
* Строка `does not escape` означает, что переменная осталась на сверхбыстром Стеке.

## 5. Разбор вывода (Inlining и Heap)
Рассмотрим лог работы компилятора при включенной оптимизации на примере чистого кода (без вызовов `fmt`).

Код `main.go`:
```go
package main

//import "fmt"

func main() {
	// var v1 int = CreateValue()
	// var v2 *int = CreatePointer()

	// fmt.Printf("v1 is: %d\n", v1)
	// fmt.Printf("value of v2 is: %d\n", *v2)

	_ = CreateValue()
	_ = CreatePointer()
}

func CreateValue() int {
	var v int = 42
	return v
}

func CreatePointer() *int {
	var v int = 99
	return &v
}
```

Вывод компилятора:
```bash
$ go build -gcflags="-m" .
./main.go:14:6: can inline CreateValue
./main.go:19:6: can inline CreatePointer
./main.go:3:6: can inline main
./main.go:10:17: inlining call to CreateValue
./main.go:11:19: inlining call to CreatePointer
./main.go:20:6: moved to heap: v
```

### Inlining (Встраивание функций)
Строки `can inline` и `inlining call to` показывают процесс **встраивания**.
Вызов функции (создание фрейма на стеке, передача аргументов) стоит процессору ресурсов. Если функция очень простая, компилятор решает её не вызывать, а просто берет её исходный код и "встраивает" (копирует) прямо в место вызова (в нашем случае — внутрь `main`).
* Таким образом, стековый кадр для встроенной функции даже **не создается** при выполнении программы!

### Почему возникает `moved to heap: v`?
Если функция `CreatePointer` была встроена в `main` и её переменные легли на стек `main`, почему компилятор всё равно сообщает, что локальная переменная `v` эвакуирована в кучу?
Дело в том, что компилятор компилирует `CreatePointer` **в двух экземплярах**:
1. Как встроенный кусок кода для `main`. Здесь всё остается на стеке (ведь указатель не покидает пределы `main`).
2. Как **самостоятельную функцию** (на случай, если кто-то из другого пакета вызовет её так, что встроить не получится).

Анализируя самостоятельный шаблон функции `CreatePointer`, компилятор видит `return &v`. Возврат указателя на локальную переменную — это гарантированный побег в кучу (`moved to heap`), иначе при завершении функции стек схлопнется, и указатель станет недействительным. Сообщение в логе относится именно к этому самостоятельному шаблону.
