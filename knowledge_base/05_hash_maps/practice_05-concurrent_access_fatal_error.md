# База Знаний: Конкурентный доступ к Мапе и Fatal Error

В Go есть железобетонное правило: **Мапы не потокобезопасны (Not Thread-Safe)**.

Если две или более горутин (потоков) обращаются к одной и той же мапе одновременно, и хотя бы одна из них записывает данные — программа мгновенно падает с фатальной ошибкой.

## Почему так сделано?
Всё упирается в эвакуацию памяти (эту тему мы разобрали ранее). Если Горутина А записывает данные в мапу, мапа может переполниться и начать эвакуацию (перенос байтов на новые адреса в Куче). Если в эту же микросекунду Горутина Б попытается прочитать или записать данные, она обратится к "мусорной" памяти или повредит внутренние указатели мапы.
Такие баги повреждения памяти (Memory Corruption) невероятно сложно отлаживать. Поэтому рантайм Go использует встроенный счетчик доступов: как только он замечает конфликт, он предпочитает "убить" программу сразу (Fail Fast), чем позволить памяти повредиться.

## Исходный код (для наглядности)
```go
 8: func main() {
 9: 	m := make(map[int]int)
10: 
11: 	fmt.Println("Запускаем бомбу замедленного действия...")
12: 
13: 	// Анонимная функция (go func), которая запускается в параллельном потоке
14: 	go func() {
15: 		for {
16: 			m[1] = 1 // Строка 16
17: 		}
18: 	}()
19: 
20: 	// Основной поток 
21: 	for {
22: 		m[2] = 2 // Строка 22
23: 	}
24: 
25: 	time.Sleep(1 * time.Second)
26: }
```

## Разбор Crash Dump (Стека вызовов при падении)

Когда программа ловит такую ошибку, она выводит подробный отчет (stack trace). Разберем его построчно, опираясь на код выше:

```text
fatal error: concurrent map writes
```
**Суть:** Ядро языка поймало одновременную запись в мапу и убило процесс. Это **не** panic, эту ошибку невозможно перехватить через `recover()`. Сервер выключается намертво.

```text
goroutine 19 [running]:
internal/runtime/maps.fatal({0x4bf87d?, 0x0?})
        /usr/local/go/src/runtime/panic.go:1046 +0x18
```
**Суть:** Авария произошла внутри Горутины 19 (номер выдается языком динамически). В момент падения она находилась в состоянии `running` (выполнялась на процессоре). Функция `maps.fatal` из внутреннего исходного кода Go — это палач, который "нажал на курок".

```text
main.main.func1()
        /home/dima/.gemini/antigravity/scratch/golang/05_hash_maps/practice_05/main.go:16 +0x28
```
**Суть:** Это самое важное место. Оно показывает, **где именно в твоем коде** произошел конфликт. В данном случае это анонимная функция `func1()` на 16-й строке (наш код `m[1] = 1`).

```text
created by main.main in goroutine 1
        /home/dima/.gemini/antigravity/scratch/golang/05_hash_maps/practice_05/main.go:14 +0x96
```
**Суть:** Показывает, **кто породил** эту аварийную Горутину 19. Её создала главная функция `main` (которая всегда является Горутиной 1) на строке 14 (там, где мы написали `go func()`).

```text
goroutine 1 [runnable]:
main.main()
        /home/dima/.gemini/antigravity/scratch/golang/05_hash_maps/practice_05/main.go:23 +0xac
```
**Суть:** Это статус главной функции `main` (Горутина 1). В момент убийства программы она находилась в состоянии `runnable` (была готова к выполнению на ядре процессора) и стояла на 23-й строке (наш код `m[2] = 2`). 

`exit status 2` — системный код возврата, означающий экстренное завершение программы.

## Как избежать этой ошибки на практике?
Если тебе нужен глобальный кэш на основе мапы, к которому будут обращаться разные запросы/горутины, мапу нужно оборачивать в структуру и защищать **Мьютексом** (`sync.RWMutex`). Мьютекс будет работать как светофор, блокируя доступ другим горутинам, пока одна из них читает или пишет данные.

Либо использовать встроенную потокобезопасную мапу `sync.Map` (для специфичных кейсов).
