# База Знаний: Анатомия hmap и Неадресуемость (Unaddressability)

В этой статье мы заглянем под капот переменной `map`, которая в Go является всего лишь 8-байтовым указателем на структуру `hmap` в Куче.

## 1. Бакеты (Buckets) и Коллизии
В отличие от массива, данные в мапе лежат не сплошным потоком. Они разбиты на блоки памяти, которые называются **бакетами (вёдрами)**. 
Каждый бакет в Go жестко вмещает ровно **8 пар ключ-значение**.

Когда ты пишешь `m["Alice"] = 25`:
1. Ключ `"Alice"` прогоняется через хэш-функцию, которая выдает число (хэш).
2. По этому хэшу Go определяет, в какое именно ведро положить данные.
3. Данные записываются в свободную ячейку (из 8) в этом ведре.

**Коллизия** возникает, когда для двух разных ключей (например, "Alice" и "Bob") алгоритм выбирает одно и то же ведро. В Go это нормально: они просто займут 1-ю и 2-ю ячейку в этом ведре. Если все 8 ячеек ведра заполнятся, Go создаст **overflow bucket (переполненное ведро)** и привяжет его к старому.

## 2. Эвакуация (Рост мапы)
Когда мапа заполняется (слишком много overflow-бакетов), Go запускает процесс **Эвакуации (Evacuation)**. Он выделяет в памяти новый, в два раза больший массив бакетов, и начинает постепенно переносить туда данные из старых вёдер.
**Важнейший факт:** Во время эвакуации твои значения *физически переезжают* на новые адреса в оперативной памяти!

## 3. Неадресуемость (Unaddressability)
Из-за того, что данные могут в любой момент физически "переехать", в Go действует строжайшее архитектурное правило: **Элементы мапы неадресуемы**.

Компилятор категорически запрещает получать указатель на элемент внутри бакета:
```go
m := map[string]int{"Alice": 25}
ptr := &m["Alice"] // ОШИБКА КОМПИЛЯЦИИ: cannot take the address
```
Если бы компилятор разрешил это, то после эвакуации твой указатель смотрел бы в старую (мусорную) память.

## 4. Загадка: Почему чтение поля разрешено, а запись — нет?
Если в мапе лежит структура, мы можем прочитать её поле, но не можем его изменить напрямую.

```go
type User struct { Age int }
users := map[string]User{"Alice": {Age: 25}}

fmt.Println(users["Alice"].Age) // ЧТЕНИЕ - РАБОТАЕТ
users["Alice"].Age = 26         // ЗАПИСЬ - ОШИБКА КОМПИЛЯЦИИ
```

### Логика компилятора:
* **Чтение** безопасно. Под капотом вызывается функция `mapaccess`, которая находит бакет и просто **копирует** байты структуры наружу. Мы читаем поле уже из этой внешней копии. Нам не нужно знать точный адрес структуры внутри бакета.
* **Запись в поле структуры** требует прямой записи байтов по точному смещению (адресу) в памяти. Но так как память бакетов "неадресуема", компилятор запрещает процессору прямой доступ к ней. Запись целиком (`users["Alice"] = newUser`) работает, потому что под капотом вызывается функция `mapassign`, которая безопасно находит бакет и перезаписывает весь блок из 8/16 байт целиком, контролируя процесс эвакуации.

## 5. Философия Go: Почему не сделали "под капотом"?
Часто возникает логичный вопрос: *Почему создатели Go не сделали так, чтобы `users["Alice"].Age = 26` работало, просто вызывая скрытую функцию `mapassign` под капотом для перезаписи одного поля?*

Технически это было возможно, но от этого отказались по трем причинам:

1. **Скрытая потеря производительности (Performance Trap).** 
   Если бы это работало, разработчики массово писали бы:
   ```go
   users["Alice"].Age = 26
   users["Alice"].Score = 100
   users["Alice"].Level = 5
   ```
   Каждая строка вызывала бы отдельное хэширование ключа "Alice" и отдельный поиск бакета в памяти. Это катастрофически медленно! Запретив прямой доступ, язык физически заставляет нас писать код, где поиск происходит только один раз:
   ```go
   // Идиоматичный способ мутации в Go:
   u := users["Alice"] // Хэширование и поиск (1 раз)
   u.Age = 26
   u.Score = 100
   u.Level = 5
   users["Alice"] = u  // Запись (1 раз)
   ```
2. **Сложность компилятора.** Поддержка глубоких вложенностей `m["A"].B[0].C = 10` с безопасным разрешением смещений внутри бакетов сделала бы компилятор Go слишком сложным.
3. **Иллюзия атомарности.** Код `users["Alice"].Age++` выглядит как одна безопасная операция. Если бы она компилировалась, программисты думали бы, что это потокобезопасно, и получали бы чудовищные гонки данных (Race Conditions) при многопоточности. Разделение на чтение и запись заставляет помнить, что мапы не потокобезопасны.
