# База Знаний: Анатомия структур в Go — Композиция, Встраивание и Механика Памяти (Стек vs Куча)

Данный документ представляет собой фундаментальное руководство уровня Middle+ по структурам данных в языке Go, их расположению в памяти, паттернам проектирования (композиция, встраивание, инкапсуляция) и исчерпывающему анализу механики аллокаций памяти (Stack vs Heap, Escape Analysis, процессорные кэш-линии и влияние на Garbage Collector).

## 1. Физическая природа структур в Go

В Go отсутствуют классы, виртуальные таблицы методов (vtable для обычных структур) и классическое наследование. Основным инструментом агрегации данных и моделирования доменной области является **структура (`struct`)**.

### 1.1. Монолитный блок памяти и Value Type
Структура в Go является **типом-значением (Value Type)**. Это означает:
1. **Непрерывный блок памяти:** Все поля структуры размещаются в оперативной памяти строго последовательно, в порядке их объявления.
2. **Побайтовое копирование:** При передаче структуры в функцию по значению (`func process(n Node)`), присваивании переменной (`a := b`) или итерации по срезу структур (`for _, item := range items`) Go производит **полное побайтовое копирование** содержимого структуры.

```go
type BaseResource struct {
    ID        int    // 8 байт
    Name      string // 16 байт (StringHeader: uintptr Data + int Len)
    Region    string // 16 байт
    CreatedAt int    // 8 байт
    status    string // 16 байт
} // Суммарно: 64 байта непрерывного блока памяти
```

### 1.2. Нулевое значение структуры (Zero Value)
В Go любая неинициализированная структура гарантированно заполняется нулями (`0x00`):
* Числовые типы (`int`, `float64`) `→` `0`
* Строки (`string`) `→` `""` (Data = nil, Len = 0)
* Булевые флаги (`bool`) `→` `false`
* Указатели, слайсы, мапы, каналы, интерфейсы `→` `nil`

#### Философия: "Make the zero value useful"
В идиоматичном коде Go структуры проектируются так, чтобы их нулевое значение было сразу готово к безопасной работе без явного вызова инициализирующих конструкторов:
* `sync.Mutex` — нулевое значение является готовым к вызову `mu.Lock()` разблокированным мьютексом.
* `bytes.Buffer` — нулевое значение готово к немедленной записи через `buf.WriteString(...)`.
* `sync.WaitGroup` — готова к `wg.Add(1)` и `wg.Wait()`.

#### Особенности возврата нулевого значения из функций
Если функция возвращает структуру по значению: `func New(...) (BaseResource, error)`, то в случае ошибки **нельзя вернуть `nil`** (компилятор выдаст ошибку: *cannot use nil as type BaseResource in return statement*).
Идиоматичный паттерн Go при ошибке — возвращать пустой литерал структуры **`BaseResource{}`**:

```go
func NewBaseResource(id, createdAt int, name, region string) (BaseResource, error) {
    if id < 0 || createdAt < 0 {
        return BaseResource{}, ErrIncorrectModelParameters // пустая структура + ошибка
    }
    // ...
}
```
При получении ошибки вызывающий код обязан проверить `if err != nil` и проигнорировать возвращенное пустое значение. Создание `BaseResource{}` не производит никаких аллокаций в куче.

## 2. Инициализация и Инкапсуляция

### 2.1. Именованные vs Позиционные литералы

```go
// Именованный литерал (СТАНДАРТ ПРОДАКШЕНА)
node := ComputeNode{
    CPU:    8,
    RAM:    16,
    HasGPU: false,
}

// Позиционный литерал (АНТИПАТТЕРН для сложных структур)
node := ComputeNode{8, 16, false}
```

* **Почему позиционный литерал опасен:** При добавлении нового поля в структуру или изменении порядка существующих полей весь код, использующий позиционные литералы, ломается с ошибкой компиляции.
* **Именованный литерал устойчив:** Новые поля автоматически получат нулевые значения, код продолжит компилироваться и работать.

### 2.2. Пакетная инкапсуляция и паттерн конструктора
В Go нет ключевых слов `private` или `public`. Доступность определяется исключительно регистром первого символа идентификатора:
* `Exported` (с заглавной буквы) — доступно внешним пакетам.
* `unexported` (со строчной буквы) — доступно **только внутри текущего пакета**.

Если структура содержит неэкспортированные поля (например, `status string`), внешний пакет не сможет инициализировать их напрямую через литерал. Для этого создается функция-фабрика (конструктор) `New...`:
1. Валидирует инварианты бизнес-логики (проверка граничных значений, пустых строк).
2. Устанавливает начальное состояние внутренних неэкспортированных полей.
3. Возвращает объект или явную ошибку `error`.

## 3. Встраивание структур (Struct Embedding) и Композиция

В Go нет наследования классов (`extends`). Вместо принципа *"является чем-то"* ("is-a") применяется принцип **композиции** (*"содержит в себе"* / "has-a").

### 3.1. Синтаксис встраивания и Promoted Fields
Встраивание структуры — это объявление поля без явного имени, только с указанием типа:

```go
type ComputeNode struct {
    model.BaseResource // Встроенная структура (анонимное поле)
    CPU    int
    RAM    int
    HasGPU bool
}
```

#### Продвижение полей (Promoted Fields):
Все экспортированные поля и методы встроенного типа автоматически "всплывают" на внешний уровень. К ним можно обращаться напрямую:

```go
node := ComputeNode{...}
fmt.Println(node.Name)       // Прямой доступ через promoted field
fmt.Println(node.GetStatus()) // Прямой вызов метода встроенной структуры
```

#### Неявное имя поля в литерале:
При инициализации внешней структуры неявным именем встроенного поля является **имя самого типа БЕЗ префикса пакета**:

```go
node := ComputeNode{
    BaseResource: base, // Ключ — "BaseResource", а не "model.BaseResource"!
    CPU:          8,
    RAM:          16,
}
```

### 3.2. Затенение (Shadowing) и Коллизии (Ambiguous Selector)
* **Затенение (Shadowing):** Если внешняя структура имеет поле с тем же именем, что и встроенная, внешнее поле затеняет внутреннее:
  ```go
  type Storage struct {
      BaseResource
      ID int // Затеняет BaseResource.ID
  }
  s := Storage{ID: 10}
  s.ID             // Обращение к Storage.ID (10)
  s.BaseResource.ID // Явное обращение к вложенному ID
  ```
* **Коллизии (Ambiguous Selector):** Если в структуру встроены две разные структуры с одинаковыми именами полей (`A.Status` и `B.Status`), прямое обращение `s.Status` вызовет ошибку компиляции: *ambiguous selector*. Обязательна явная квалификация: `s.A.Status` или `s.B.Status`.

### 3.3. Анонимные структуры (Anonymous Structs)
Структура может быть объявлена локально без создания именованного типа через `type`:

```go
report := struct {
    TotalNodes   int
    TotalVolumes int
    TotalCPU     int
}{
    TotalNodes:   len(nodes),
    TotalVolumes: len(volumes),
    TotalCPU:     totalCPU,
}
```

**Когда применять:**
1. **Table-driven тесты:** Формирование срезов тестовых кейсов: `tests := []struct{ name string; in int; want int }{ ... }`.
2. **Локальные одноразовые отчеты и сводки:** Избавляет проект от мусорных глобальных типов, используемых ровно один раз.
3. **Разовый парсинг специфичного JSON:** Десериализация вложенного ответа внешнего API, когда из огромного JSON нужны 2-3 поля.

## 4. Конечный автомат (State Machine) на `switch`

При валидации переходов состояний сущности (например, жизненного цикла ресурса) использование цепочки `if-else` провоцирует скрытые баги и снижает читаемость.

### Идиоматичный шаблон переходов состояний:
```go
func (br *BaseResource) SetStatus(newStatus string) error {
    oldStatus := br.GetStatus()

    switch oldStatus {
    case "PROVISIONING":
        if newStatus != "RUNNING" {
            return ErrIncorrectNextStatus
        }

    case "RUNNING":
        if newStatus != "STOPPED" && newStatus != "TERMINATED" {
            return ErrIncorrectNextStatus
        }

    case "STOPPED":
        if newStatus != "RUNNING" {
            return ErrIncorrectNextStatus
        }

    default:
        // Обрабатывает пустой статус, "TERMINATED" (нет переходов) и любые невалидные строки
        return ErrIncorrectNextStatus
    }

    // В Go нет неявного fallthrough: если case завершился без return, 
    // управление выходит из switch. Присваивание пишется ровно 1 раз:
    br.status = newStatus
    return nil
}
```

## 5. Глубокий анализ механики памяти: Стек против Кучи

Это ключевой раздел, систематизирующий вопросы об аллокациях, сборщике мусора и устройстве памяти в Go.

### 5.1. Стек (Stack) vs Куча (Heap)

| Характеристика | Стек (Stack) | Куча (Heap) |
| :--- | :--- | :--- |
| **Принцип работы** | Выделяется под стек-фрейм горутины/функции. | Глобальное динамическое пространство памяти процесса. |
| **Скорость аллокации** | Наносекунды (сдвиг регистра указателя стека `SP`). | Медленнее (поиск блока в аллокаторе `mcache` / `mcentral`). |
| **Освобождение памяти** | Мгновенно при выходе из функции (сдвиг `SP` назад). | Требует циклов сканирования Сборщиком Мусора (GC). |
| **Участие GC** | **Сборщик мусора НЕ участвует вообще.** | **GC регулярно сканирует все живые объекты.** |
| **Потокобезопасность** | Локален для конкретной горутины, без блокировок. | Разделяется между всеми горутинами. |

---

### 5.2. Анализ побега (Escape Analysis)

Go гарантирует безопасность работы с памятью. Программист не выделяет память вручную (`malloc` / `free`). Решение о том, где будет жить переменная, принимает компилятор на этапе сборки с помощью **Escape Analysis (Анализа побега)**.

Главный закон Escape Analysis:
> **Если время жизни переменной не превышает время выполнения функции, в которой она создана, и её адрес не утекает наружу — переменная размещается на СТЕКЕ.**
> **Если переменная должна жить ДОЛЬШЕ, чем вызвавший её фрейм функции (например, возвращается её адрес `*T`), она "сбегает" в КУЧУ (escapes to heap).**

#### Разбор трех сценариев возврата из функции:

#### Сценарий А: Возврат структуры по значению
```go
func create() BaseResource {
    b := BaseResource{ID: 1}
    return b
}
```
* `b` создается на стеке `create()`.
* При `return b` Go побайтово копирует 64 байта со стека `create()` в стек вызывающей функции (`main`).
* Стек-фрейм `create()` очищается.
* **Результат: 0 аллокаций в куче, чистый стек.**

#### Сценарий Б: Возврат указателя на структуру
```go
func create() *BaseResource {
    b := BaseResource{ID: 1}
    return &b // Возврат указателя наружу!
}
```
* Компилятор видит: адрес `&b` возвращается вызывающей функции, значит память должна жить после завершения `create()`.
* На стеке `create()` её оставлять нельзя (иначе после выхода из функции память перезапишется).
* Компилятор директивой `moved to heap: b` выделяет память в **куче**.
* В `main` возвращается 8-байтный адрес на кучу.
* **Результат: 1 аллокация в куче. Память отслеживается Garbage Collector.**

#### Сценарий В: Создание через указатель внутри функции, но возврат по значению (Разыменование)
```go
func create() BaseResource {
    ptr := &BaseResource{ID: 1}
    return *ptr // Разыменовали!
}
```
* **Останется ли объект на стеке? ДА!**
* Escape Analysis анализирует: вышел ли адрес `ptr` наружу? **Нет!**
* Адрес использовался исключительно внутри функции для чтения значения. Наружу через `return` пошло побайтовое копирование самого значения.
* Компилятор видит, что адрес за пределы функции не утек, и оптимизирует: объект аллоцируется **на стеке**, без выхода в кучу.

### 5.3. Почему в исходном коде произошла паразитная аллокация в куче?

Вспомним связку из первой итерации:
```go
// model.go
func NewBaseResource(...) (*BaseResource, error) {
    return &BaseResource{...}, nil // 1. Адрес утек наружу -> Куча!
}

// compute_node.go
func NewComputeNode(...) (*ComputeNode, error) {
    br, _ := model.NewBaseResource(...) // br указывает на память в куче
    return &ComputeNode{
        BaseResource: *br, // 2. Разыменование и копирование
    }, nil
}
```

Что произошло физически:
1. `NewBaseResource` выделил `BaseResource` (64 байта) в **куче**, потому что вернул указатель `*BaseResource`.
2. `NewComputeNode` вызвал `NewBaseResource` и получил указатель на кучу.
3. Поскольку поле `BaseResource` встроено **по значению**, `ComputeNode` — это единый монолитный блок на 88 байт. Чтобы собрать эти 88 байт, процессор **скопировал 64 байта из кучи** в составной объект `ComputeNode`.
4. Исходный объект `BaseResource` в куче стал не нужен — он превратился в «мертвый груз» для GC.
5. **Вывод:** Возвращать указатель из вспомогательного конструктора, если целевая структура встраивает его по значению — это двойная работа процессора (аллокация в куче + побайтовое копирование + мусор для GC).
6. **Правильное решение:** `NewBaseResource` должен возвращать значение: `(BaseResource, error)`. Тогда вся цепочка конструирования отрабатывает на быстрых стеках функций.

### 5.4. Встраивание по значению (`BaseResource`) vs Встраивание по указателю (`*BaseResource`)

Почему не встраивать везде указатели `*BaseResource`, чтобы никогда не копировать байты?

#### Сравнение схем в памяти:

```text
1. Встраивание ПО ЗНАЧЕНИЮ (type ComputeNode struct { BaseResource; ... }):
[----------------------- Единый блок: 88 байт -----------------------]
[ ID (8B) | Name (16B) | Region (16B) | CreatedAt (8B) | status (16B) | CPU (8B) | RAM (8B) | GPU (1B) | Pad (7B) ]
-> Все поля лежат в памяти вплотную друг к другу.

2. Встраивание ПО УКАЗАТЕЛЮ (type ComputeNode struct { *BaseResource; ... }):
[--- ComputeNode: 32 байта ---]            [---------- BaseResource в куче: 64 байта ----------]
[ *BaseResource (8 байт ptr) ] ----------> [ ID | Name | Region | CreatedAt | status ]
[ CPU (8B) | RAM (8B) | GPU+Pad (8B) ]
-> Два независимых куска памяти, разнесенных по адресам RAM!
```

### 5.5. Почему указатели в куче часто МЕДЛЕННЕЕ копирования по стеку?

Существует два фундаментальных фактора аппаратного уровня:

#### 1. Локальность кэша процессора (L1/L2 Cache Locality)
* Современные процессоры считывают память из RAM не байтами, а **кэш-линиями (Cache Lines) размером 64 байта**.
* **При монолитной структуре (по значению):** Процессор за 1 такт затягивает структуру в L1-кэш. Чтение полей происходит практически со скоростью регистров процессора (1-2 наносекунды).
* **При структуре с указателем:** Чтобы прочитать `node.BaseResource.Name`, процессору сначала нужно прочитать указатель из `ComputeNode`, а затем сделать прыжок по адресу в кучу (**Pointer Chasing**). Память в куче лежит в другом месте — происходит **промах мимо кэша (Cache Miss)**. Процессор вынужден обращаться к медленной шине RAM, что в **100–200 раз медленнее**!

#### 2. Нагрузка на сборщик мусора (Garbage Collector Overhead)
GC в Go работает по алгоритму **Mark-and-Sweep (Трассировка)**:
Чтобы освободить мусор, сборщик обязан пройти по всем живым указателям в памяти.

#### Мысленный эксперимент: Сервис хранит реестр на 500 000 узлов

* **Вариант А: Срез монолитных структур (`[]ComputeNode`)**
  * Память: Go выделяет в куче **всего 1 непрерывный массив**:
    `500 000 * 88 байт ≈ 44 МБ`.
  * Для GC это **ровно 1 объект в куче**!
  * GC помечает блок целиком за доли миллисекунды.

* **Вариант Б: Срез указателей на структуры с встроенными указателями (`[]*ComputeNode`, где внутри `*BaseResource`)**
  * В куче лежат:
    * 500 000 объектов `ComputeNode`
    * 500 000 отдельных объектов `BaseResource`
  * **ИТОГО: 1 000 000 независимых объектов в куче!**
  * Плюс 1 000 000 указателей-ссылок между ними.
  * При сканировании GC вынужден выполнить **1 миллион прыжков по памяти**, проверяя каждую ссылку. Нагрузка на процессор возрастает на порядки, порождая всплески времени отклика (latency spikes / stop-the-world phases).

### 5.6. Тонкости итерирования в цикле `range`

В Go цикл `for range` имеет важную механику работы с памятью:

```go
// 1. Обход по значению (ОПАСНО для больших коллекций и мутаций):
for _, node := range nodes {
    // На КАЖДОЙ итерации вся структура node (88 байт) ПОБАЙТОВО КОПИРУЕТСЯ 
    // во временную переменную node!
    
    node.SetStatus("RUNNING") 
    // ЛОВУШКА! node - это локальная копия! Метод изменит статус у копии, 
    // а элемент в срезе nodes останется неизменным!
}

// 2. Идиоматичный обход по индексу (ЭФФЕКТИВНО):
for i := range nodes {
    // Ноль байт копирования структуры!
    totalCPU += nodes[i].CPU
    nodes[i].SetStatus("RUNNING") // Статус изменится у РЕАЛЬНОГО элемента среза!
}
```

## 6. Шпаргалка для диагностики Escape Analysis

Чтобы узнать, куда компилятор поместил переменную, используется флаг компилятора `-gcflags="-m"`:

```bash
$ go build -gcflags="-m" main.go
```

### Значения сообщений компилятора:
* `... does not escape` `→` Переменная гарантированно осталась на **стеке** (быстро, GC не участвует).
* `... escapes to heap` `→` Переменная улетела в **кучу** (время жизни вышло за пределы функции, участвует GC).
* `... moved to heap` `→` Создана локально, но вынесена в кучу из-за утечки указателя.

## 7. Вопросы с собеседований (Self-Check Q&A)

### В: Чем встраивание структур (`embedding`) отличается от наследования в ООП?
**О:** В Go нет полиморфизма подтипов и vtable для структур. Встраивание — это синтаксический сахар над композицией: поля и методы вложенной структуры продвигаются (`promoted`) на внешний уровень, но внешняя структура **не становится тем же типом**, что и внутренняя (нельзя передать `ComputeNode` в функцию, принимающую `BaseResource`).

### В: Почему возврат по указателю `*T` из конструктора не всегда является лучшей практикой?
**О:** Если структура имеет небольшой размер (до 100–200 байт) и встраивается в другие типы по значению, возврат указателя заставляет Escape Analysis аллоцировать её в куче, создавая лишнюю нагрузку на GC и теряя локальность кэша процессора. Возврат по значению `(T, error)` полностью бесплатен для GC и выполняется на стеке.

### В: Если внутри функции создать указатель `ptr := &MyStruct{}` и вернуть разыменованное значение `return *ptr`, будет ли аллокация в куче?
**О:** Нет. Escape Analysis проверяет, утек ли адрес переменной за пределы времени жизни функции. Поскольку наружу возвращается копия значения, а сам адрес остался замкнутым внутри функции, компилятор разместит структуру на стеке.

### В: Почему срез значений `[]MyStruct` лучше для Garbage Collector, чем срез указателей `[]*MyStruct`?
**О:** Срез значений `[]MyStruct` аллоцируется в куче как единый непрерывный плоский буфер (1 объект для GC). Срез указателей `[]*MyStruct` порождает N независимых объектов в куче, каждый из которых GC обязан индивидуально просканировать и отследить.
