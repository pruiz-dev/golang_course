# База Знаний: Идиоматичная мутация Слайсов в функциях

## 1. Проблема: "Потерянный лут" при переаллокации
Слайс передается в функции **по значению** (копируется 24-байтовый заголовок `SliceHeader`). Указатель внутри копии продолжает смотреть на оригинальный базовый массив.

Из-за этого возникает классическая ошибка:
```go
func main() {
    inventory := []string{"Меч"}
    addLoot(inventory)
    // inventory всё еще содержит только "Меч"!
}

func addLoot(items []string) {
    items = append(items, "Золото") // ОШИБКА АРХИТЕКТУРЫ
}
```
**Что пошло не так?**
Функция `append` увидела, что вместимость (`cap`) закончилась. Она выделила новый массив в Куче, записала туда "Золото" и обновила указатель в **локальной копии** заголовка `items`. Функция завершилась, локальный `items` умер, а оригинальный `inventory` так и остался указывать на старый массив.

---

## 2. Решение "в лоб" (Стиль C++ / Java)
Технически, чтобы функция могла изменить саму переменную `inventory` (её заголовок), можно передать **указатель на слайс**:

```go
// ПЛОХОЙ СТИЛЬ (Unidiomatic Go)
func main() {
    inventory := []string{"Меч"}
    addLoot(&inventory) // Передаем адрес самого заголовка
}

func addLoot(itemsPtr *[]string) {
    // Разыменовываем указатель, чтобы добраться до слайса
    *itemsPtr = append(*itemsPtr, "Золото") 
}
```
**Почему в Go так писать НЕ принято?**
1. **Сложность чтения:** Код пестрит звездочками `*` и амперсандами `&`. Читать цепочки `*itemsPtr` физически больно.
2. **Двойная косвенность (Double Indirection):** Указатель на структуру, внутри которой лежит еще один указатель на память. Это создает излишнюю нагрузку на процессор при разыменовании.
3. **Нарушение конвенций языка:** В Go слайсы специально созданы как легковесные (24 байта) дескрипторы именно для того, чтобы передавать их по значению.

---

## 3. Решение "По-Goшному" (Идиоматичный стиль)
Золотой стандарт языка Go — принимать слайс по значению и **возвращать измененный слайс обратно**, заставляя вызывающую сторону переприсвоить переменную.

```go
// ХОРОШИЙ СТИЛЬ (Idiomatic Go)
func main() {
    inventory := []string{"Меч"}
    
    // Явное переприсваивание
    inventory = addLoot(inventory) 
}

func addLoot(items []string) []string {
    items = append(items, "Золото")
    return items // Возвращаем новый 24-байтовый заголовок
}
```
**Почему это архитектурный идеал?**
1. **Чистота и ясность:** Код читается как английское предложение: *"inventory становится результатом addLoot от inventory"*. Никаких скрытых мутаций памяти. Разработчик в функции `main` явно видит, что переменная будет перезаписана.
2. **Единообразие:** Именно по такому принципу спроектирована встроенная функция `append()`: она возвращает новый слайс, который мы обязаны переприсвоить (`s = append(s, val)`). Использование этого же паттерна в твоем коде делает его предсказуемым для любого другого Go-разработчика.
3. **Скорость:** Копирование 24 байт при возврате из функции для процессора происходит практически бесплатно (в регистрах).
