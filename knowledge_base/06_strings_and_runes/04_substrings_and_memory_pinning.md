# База Знаний: Подстроки, Утечки памяти (Memory Pinning) и strings.Clone

## 1. Концептуальное понимание: Что такое `strings.Clone` простыми словами?

Чтобы понять смысл `strings.Clone` без кода, представь жизненную аналогию:

### Аналогия с энциклопедией:
* **Наивный срез (`s[start:end]`):**  
  Тебе в руки попала 1000-страничная тяжелая энциклопедия (100 МБ данных). Тебе из нее нужна всего одна цитата из 5 слов (16 байт).  
  Ты наклеиваешь бумажную закладку на страницу с этой цитатой и... **кладешь всю 10-килограммовую энциклопедию себе в рюкзак**.  
  Каждый раз, когда тебе нужна цитата, ты открываешь рюкзак и читаешь по закладке. Ты не можешь выбросить огромную книгу на переработку, потому что закладка приклеена к ее странице!  
  Если ты сделаешь так 100 раз — твой рюкзак разорвется от тонн макулатуры.

* **`strings.Clone`:**  
  Ты берешь маленький стикер (чистый кусочек памяти), аккуратно **переписываешь на него эти 5 слов**, кладешь стикер в карман, а гигантскую тяжелую энциклопедию **немедленно выбрасываешь в мусорный бак** (Garbage Collector).  
  В кармане у тебя лежит легкий листок на 1 грамм, а рюкзак абсолютно пуст.

## 2. Разница в памяти: Срез vs Заголовок строки vs Полезная нагрузка

Разберем, почему в коде фигурируют числа 24 байта, 16 байт и 131 КБ:

```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Срез clonedTokens ([]string) на стеке: 24 байта                     │
│    [ Data (8 байт) | Len: 10 (8 байт) | Cap: 10 (8 байт) ]            │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ указывает на массив из 10 строк
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. Массив элементов string в куче: 10 штук * 16 байт = 160 байт        │
│    Каждый элемент — это StringHeader:                                  │
│    [ Data: 0x9000 (8 байт) | Len: 16 (8 байт) ]                       │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ указывает на чистые байты
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. Полезная нагрузка токена в куче: 16 физических байт                 │
│    [ 'T', 'O', 'K', 'E', 'N', '_', '9', '8', '7', '6', ... ]           │
└────────────────────────────────────────────────────────────────────────┘
```

1. **24 байта (`SliceHeader`):** это заголовок самого среза `clonedTokens` (`Data`, `Len`, `Cap`).
2. **16 байт (`StringHeader`):** это заголовок каждой отдельной строки внутри среза (`Data`, `Len`).
3. **16 байт полезной нагрузки:** это сам текст `"TOKEN_9876543210"` (`len = 16`).
4. **Почему наивный срез держал 100 МБ?**  
   Потому что `Data` наивной строки смотрел не в изолированные 16 байт, а в **громадный массив размером 10 485 760 байт (10 МБ)**, не давая сборщику мусора его освободить!

## 3. Механика подстрок: Как работает `s[start:end]` под капотом

В Go взятие подстроки — это операция со сложностью **O(1) по времени и 0 байт аллокаций памяти**.

```go
s := "HELLO WORLD" // Адрес 0x1000, длина 11
sub := s[6:11]      // Подстрока "WORLD" (start = 6, end = 11)
```

### Что делает процессор при `start != 0`:
Процессор выполняет ровно две машинные инструкции за 1 такт:
1. **Сложение для адреса:** `sub.Data = s.Data + 6` -> `0x1000 + 6 = 0x1006` (адрес буквы 'W').
2. **Вычитание для длины:** `sub.Len = end - start` -> `11 - 6 = 5`.

```
Заголовок s (16 байт):
┌─────────────────────────┬─────────────────────────┐
│ Data: 0x1000            │ Len: 11                 │
└────────────┬────────────┴─────────────────────────┘
             │
Заголовок sub (16 байт):
┌────────────┴────────────┬─────────────────────────┐
│ Data: 0x1006            │ Len: 5                  │
└─────────────────────────┴─────────────────────────┘
             │                          │
             ▼                          ▼
Память в куче:
[ 'H', 'E', 'L', 'L', 'O', ' ', 'W', 'O', 'R', 'L', 'D' ]
                                 ▲
                     sub смотрит прямо сюда
```

Ни одного байта текста не копируется. В куче ничего не выделяется.

## 4. Феномен Memory Pinning (Удержание памяти в куче)

Пока существует переменная `sub`, весь исходный массив **неделим и приколот (pinned) к памяти**:
* Если исходная строка весила **50 МБ**, а подстрока — **16 байт**, в памяти останутся все **50 МБ**.
* 1 000 таких подстрок в кэше сервиса будут удерживать **50 ГБ оперативной памяти** вместо 16 КБ.
* Сервис неминуемо упадет по ошибке `Out Of Memory (OOM)`.

## 5. Внутреннее устройство `strings.Clone` (Go 1.18+)

```go
func Clone(s string) string {
    if len(s) == 0 {
        return ""
    }
    b := make([]byte, len(s))
    copy(b, s)
    return *(*string)(unsafe.Pointer(&b))
}
```

### 1. Почему `copy(b, s)` принимает строку?
В спецификации Go заложено специальное исключение: `copy(dst []byte, src string) int`.  
Компилятор транслирует этот вызов в ассемблерную инструкцию `memmove`, которая копирует байты из строки в новый срез через быстрые векторные SIMD-регистры процессора.

### 2. Зачем нужен `*(*string)(unsafe.Pointer(&b))`?
* `&b` — берет адрес среза `*[]byte`.
* `unsafe.Pointer(&b)` — сбрасывает проверку типов до универсального адреса.
* `(*string)(...)` — указывает компилятору интерпретировать первые 16 байт среза (`Data` и `Len`) как строку, игнорируя `Cap`.
* `*` — разыменовывает указатель в готовую строку.
* **Цель трюка:** избежать повторного копирования памяти, которое произошло бы при обычном `string(b)`.

## 6. Liveness Analysis: Почему порядок строк изменил замер с 100 МБ до 131 КБ?

В лабораторной практике мы столкнулись с тонким поведением компилятора:

### Случай 1 (Утечка видна в обоих замерах):
```go
printMemUsage("После strings.Clone") // Замер памяти
fmt.Println(naiveTokens[0] == clonedTokens[0]) // naiveTokens еще нужен!
```
Так как обращение к `naiveTokens` идет **после** замера, компилятор держит его живым. Вызов `runtime.GC()` внутри замера не может освободить 100 МБ.

### Случай 2 (Утечка исчезла):
```go
fmt.Println(naiveTokens[0] == clonedTokens[0]) // ПОСЛЕДНЕЕ обращение к naiveTokens!
printMemUsage("После strings.Clone") // Замер памяти
```
Благодаря **Liveness Analysis** компилятор видит, что после строки сравнения к `naiveTokens` больше нет обращений. Переменная объявляется мертвой. Пришедший `runtime.GC()` стирает 100 МБ старых массивов, и память падает до 131 КБ.

## 7. Откуда берутся 131 КБ (почему не 0)?

131 КБ — это базовый минимальный уровень фонового потребления кучи рантаймом Go:
1. **Инициализация пакетов:** структуры пакетов `fmt`, `runtime`, `unicode/utf8`.
2. **Страницы аллокатора (mcache / spans):** Go выделяет память блоками минимум по 8 Килобайт.
3. **Метаданные сборщика мусора и горутин.**
