# База Знаний: Конкатенация строк, bytes.Buffer и strings.Builder под капотом

## 1. Фундамент: Что такое строка в памяти Go?

В Go строка (`string`) — это не массив символов и не просто сырой указатель. На 64-битной архитектуре переменная типа `string` занимает ровно **16 байт** и описывается структурой `StringHeader`:

```go
type StringHeader struct {
    Data uintptr // 8 байт: прямой адрес первого байта в оперативной памяти
    Len  int     // 8 байт: количество физических БАЙТОВ в строке
}
```

```
Переменная s (16 байт на стеке):
┌─────────────────────────┬─────────────────────────┐
│ Data: 0x1000 (8 байт)   │ Len: 12 (8 байт)        │
└────────────┬────────────┴─────────────────────────┘
             │
             ▼
Физический массив байтов в куче или .rodata:
[ 0xD0, 0x9F, 0xD1, 0x80, ... ] (12 байт слова "Привет")
```

### Главный закон языка: Иммутабельность
Байты строки в памяти **навечно защищены от записи (Read-Only)**. Ни рантайм, ни компилятор не разрешают перезаписать байт по адресу `0x1000`. Это необходимо для:
1. **Безопасности конкурентности:** сотни горутин могут читать одну строку без мьютексов и гонок данных (Data Race).
2. **Оптимизации ОС:** строковые литералы лежат в неизменяемом сегменте `.rodata`.
3. **Дешевой передачи:** передача строки в функцию копирует лишь 16 байт заголовка.

## 2. Проблема оператора `+` в цикле (Квадратичная сложность O(N^2))

Когда мы складываем две строки:
```go
s1 := "Привет"
s2 := ", мир!"
s3 := s1 + s2
```
Рантайм Go не имеет права дописать байты `s2` в конец `s1`. Он обязан:
1. Выделить в куче **новый блок памяти** размером `len(s1) + len(s2)`.
2. Скопировать байты `s1`.
3. Скопировать байты `s2`.
4. Вернуть новую строку `s3`.

### Эффект снежного кома в цикле
Представим, что мы собираем строку из N = 4 шагов, добавляя по 10 байт:
```go
var s string
s += "1234567890" // Шаг 1: выделено 10 байт, скопировано 10 байт
s += "1234567890" // Шаг 2: выделено 20 байт, скопировано старых 10 + новых 10 = 20 байт
s += "1234567890" // Шаг 3: выделено 30 байт, скопировано старых 20 + новых 10 = 30 байт
s += "1234567890" // Шаг 4: выделено 40 байт, скопировано старых 30 + новых 10 = 40 байт
```

Суммарно процессор скопировал:
`10 + 20 + 30 + 40 = 100 байт!`
Хотя итоговая строка весит всего **40 байт**. А старые куски (на 10, 20 и 30 байт) брошены в куче как мусор для Garbage Collector.

### Катастрофа на 50 000 итераций
Если кусочек весит 11 байт (`"log record\n"`), а итераций N = 50 000:
Суммарный объем перекопированных процессором байтов вычисляется по формуле суммы арифметической прогрессии:
`Размер_кусочка * (1 + 2 + 3 + ... + N) = Размер_кусочка * N * (N + 1) / 2`

Подставляем числа:
`11 * (50 000 * 50 001 / 2) = 11 * 1 250 025 000 операций ≈ 13.7 ГИГАБАЙТ памяти!`

* **Итоговый результат:** строка весит всего **550 килобайт**.
* **Цена наивности:** процессор перелопатил **13.7 ГБ памяти** в куче и создал 50 000 временных объектов. Программа зависает на секунды, нагружая сборщик мусора. Сложность алгоритма — **O(N^2)**.

## 3. `bytes.Buffer`: Универсальный буфер ввода-вывода

Чтобы избежать постоянных аллокаций, исторически использовался `bytes.Buffer` из пакета `"bytes"`.

### Что у него под капотом?
```go
type Buffer struct {
    buf      []byte // Мутабельный срез байтов (Data, Len, Cap)
    off      int    // Смещение чтения (read offset)
    lastOp   readOp // Для поддержки UnreadRune / UnreadByte
}
```

Срез `buf []byte` имеет поле **`Cap` (вместимость)**. При записи данных он геометрически удваивает свой размер (например: 64 -> 128 -> 256...), позволяя дописывать новые байты в свободный `Cap` без перевыделения памяти на каждой итерации.

### Методы записи: байты, числа и руны
1. **`buf.WriteByte(c byte)`:**
   - В Go `byte` — это алиас для `uint8` (диапазон чисел от `0` до `255`).
   - Можно передать как символ в одинарных кавычках (`buf.WriteByte(' ')` или `buf.WriteByte('A')`), так и любое число: `buf.WriteByte(65)` (запишет код символа `'A'`) или `buf.WriteByte(255)`.
   - Метод записывает ровно **1 физический байт** в конец буфера и увеличивает `Len` на 1.

2. **`buf.WriteRune(r rune)`:**
   - В Go `rune` — это алиас для `int32` (кодовая точка стандарта Unicode, до `0x10FFFF`).
   - Если передать руну `'🚀'` (`U+1F680`):
     - Метод `WriteRune` не может записать 4-байтный `int32` целиком как есть.
     - Он кодирует руну в поток **UTF-8** (от 1 до 4 байт).
     - Для `'🚀'` генерируется последовательность из 4 байтов: `[0xF0, 0x9F, 0x9A, 0x80]`.
     - Эти 4 байта дописываются в конец среза `buf`, а `Len` увеличивается на 4.

### Как работает вычитывание рун (`buf.ReadRune()`)?
`bytes.Buffer` реализует интерфейс `io.RuneReader`:
```go
r, size, err := buf.ReadRune()
```
* **Механика под капотом:**
  1. Буфер смотрит на первый байт по смещению `off`.
  2. По старшим битам первого байта декодер UTF-8 определяет длину символа:
     - `0xxxxxxx` -> 1 байт (ASCII)
     - `110xxxxx` -> 2 байта
     - `1110xxxx` -> 3 байта
     - `11110xxx` -> 4 байта (как у `'🚀'`)
  3. Декодер читает оставшиеся 3 байта, проверяет валидность UTF-8 префиксов `10xxxxxx`.
  4. С помощью битовых сдвигов и масок он собирает эти 4 байта обратно в 32-битное число `rune` (`U+1F680`).
  5. Смещение чтения сдвигается вперед: `b.off += 4`.
  6. Возвращается руна `'🚀'` и количество прочитанных байт `size = 4`.

### Зачем нужно поле `off int`?
`bytes.Buffer` — это двусторонняя труба (FIFO-очередь): в него можно **писать** (`Write`) и из него можно **вычитывать** (`Read`).
* `off` — это курсор/закладка чтения: с какого байта начинаются еще непрочитанные данные.
* Когда ты читаешь 5 байт из буфера, буфер не сдвигает весь массив влево (это было бы медленно). Он просто делает `off += 5`.
* Непрочитанный остаток буфера — это срез `b.buf[b.off:]`.

### Черный ящик: Что делает `buf.String()`?
Когда мы вызываем `buf.String()`, в исходниках Go выполняется:
```go
func (b *Buffer) String() string {
    if b == nil {
        return "<nil>"
    }
    return string(b.buf[b.off:])
}
```

Конструкция `string(срез_байт)` — это **принудительное полное копирование**:
1. Go вызывает рантайм-функцию `runtime.slicebytetostring`.
2. Менеджер памяти выделяет в куче **новый блок памяти** размером с буфер.
3. Инструкция процессора `memmove` байт за байтом переносит данные в новый блок.
4. Создается строка `StringHeader`, указывающая на этот новый блок.

> **Зачем Go это делает?**  
> Чтобы защитить иммутабельность строки! Если бы строка смотрела прямо в `b.buf`, то последующее изменение буфера (`b.WriteByte(...)`) изменило бы содержимое уже отданной строки.

**Минус `bytes.Buffer` для сборки строк:**  
Если буфер накопил 100 МБ отчета, финальный вызов `.String()` выделит **еще 100 МБ** в куче и скопирует их заново.

## 4. `strings.Builder`: Zero-Copy революция (Go 1.10+)

`strings.Builder` разработан специально для высокопроизводительной сборки строк без накладных расходов.

### Внутреннее устройство `strings.Builder`
```go
type Builder struct {
    addr *Builder // 8 байт: указатель на самого себя (защита от копирования)
    buf  []byte   // 24 байта: SliceHeader (Data, Len, Cap)
}
```
Структура занимает всего **32 байта**.

---

### Механика Zero-Copy: Как надевается «ярлык» строки на срез?

В исходниках Go метод `String()` написан так:
```go
func (b *Builder) String() string {
    return *(*string)(unsafe.Pointer(&b.buf))
}
```

Разберем этот трюк на уровне памяти:
```
Срез b.buf (24 байта в памяти):
┌──────────────────────┬──────────────────────┬──────────────────────┐
│ Data: 0x5000 (8 байт)│ Len: 10 (8 байт)     │ Cap: 32 (8 байт)     │
└──────────┬───────────┴──────────┬───────────┴──────────────────────┘
           │                      │                  ▲
           ▼                      ▼                  │
┌──────────────────────┬──────────────────────┐      │
│ Data: 0x5000 (8 байт)│ Len: 10 (8 байт)     │  (Cap отбрасывается!)
└──────────────────────┴──────────────────────┘
Строка string (16 байт):
```

#### Почему это работает?
1. В памяти срез описывается тремя 8-байтными полями: `[Data, Len, Cap]`.
2. Строка описывается двумя 8-байтными полями: `[Data, Len]`.
3. Указатель `&b.buf` указывает на начало среза (на поле `Data`).
4. Приведение `*(*string)(unsafe.Pointer(&b.buf))` указывает рантайму:  
   *«Интерпретируй эти 24 байта памяти как структуру строки из 16 байт»*.
5. Рантайм берет первые 16 байт (`Data` и `Len`), формируя готовую структуру `string`.
6. Поле `Cap` (последние 8 байт) просто игнорируется! Строка даже не знает, что там был какой-то `Cap`.
7. **Результат:** 0 байт аллокаций, 0 наносекунд на копирование!

### Почему не нарушается иммутабельность строки?

Возникает фундаментальный вопрос:  
*«Если строка смотрит прямо во внутренний массив билдера, что будет, если мы продолжим писать в билдер после вызова `.String()`?»*

В Go это решено на уровне архитектуры тремя принципами:

#### 1. Принцип Append-Only (Запись только в хвост)
`strings.Builder` умеет писать **только в конец**. В нем нет методов изменения ранее записанных байт:
* Пусть мы записали `"Hello"` и вызвали `s1 := sb.String()`.
* Строка `s1` зафиксировала длину `Len = 5` и адрес первого байта `Data = 0x5000`.
* Затем мы вызвали `sb.WriteString(" World")`.
* Билдер запишет `" World"` в ячейки с индексами 5 по 10.
* **Первые 5 ячеек (где лежит "Hello") физически не изменяются!**
* Строка `s1` читает строго свои 5 байт от адреса `0x5000` до смещения 5. Для нее ничего не изменилось!
* Новая строка `s2 := sb.String()` будет иметь `Data = 0x5000`, но `Len = 11`.

#### 2. Поведение при превышении емкости (Cap Overflow / Grow)
Что произойдет, если емкость `Cap` старого массива исчерпана и билдеру нужно расшириться?
* Билдер выделяет в куче **новый, больший массив байт** (например, по адресу `0x9000`).
* Он копирует накопленные данные туда и продолжает писать в новый массив.
* Старый массив по адресу `0x5000` **не уничтожается**! На него продолжает ссылаться строка `s1`. Сборщик мусора (GC) не тронет старый массив, пока жива `s1`.
* Будущие записи в билдер вообще происходят по адресу `0x9000` и никак не могут пересечься со старым массивом.

#### 3. Метод `Reset()`: почему `b.buf = nil`, а не `b.buf = b.buf[:0]`
В обычном `bytes.Buffer` метод `Reset()` делает:
```go
b.buf = b.buf[:0] // Сохраняет старый массив, просто сбрасывая Len в 0!
```
Если бы `strings.Builder` сделал так же, произошла бы катастрофа:
1. Строка `s1` смотрит на ячейки 0..4 старого массива (`"Hello"`).
2. Вызываем `sb.Reset()`. Если бы он сделал `b.buf = b.buf[:0]`, емкость осталась бы старой, а длина стала 0.
3. Следующая запись `sb.WriteString("ALERT")` перезаписала бы ячейки 0..4 прямо поверх `"Hello"`!
4. Иммутабельная строка `s1` неожиданно превратилась бы в `"ALERT"`!

Именно поэтому разработчики Go реализовали `Reset()` в `strings.Builder` так:
```go
func (b *Builder) Reset() {
    b.addr = nil
    b.buf = nil // ПОЛНОЕ обнуление среза!
}
```
Билдер **навсегда разрывает связь со старым массивом** и забывает его. Старый массив целиком отдается во владение ранее созданной строке `s1`, а новая запись в билдер начнется в абсолютно новом срезе с нуля.

### Защита от копирования по значению (`addr *Builder`)

Почему нельзя передавать `strings.Builder` в функцию по значению (`b2 := b1`)?

#### Сценарий катастрофы при копировании структуры:
```go
var b1 strings.Builder
b1.WriteString("hello")

b2 := b1 // Скопировали 32 байта структуры на новое место стека!
```
1. `b1` и `b2` теперь две разные переменные, но их поля `buf.Data` указывают **на один и тот же массив байтов в куче**.
2. У обоих длина `Len = 5` и одинаковый `Cap`.
3. Теперь выполняем:
   ```go
   b1.WriteString(" AAA")
   b2.WriteString(" BBB")
   ```
4. Оба билдера думают, что их свободный хвост начинается с 5-го байта.
5. Они оба пишут в одни и те же ячейки памяти, перезаписывая байты друг друга! Возникает повреждение памяти (Data Corruption).

#### Как рантайм Go ловит нарушителя:
Для предотвращения этой ошибки в структуре есть поле `addr *Builder`:
```go
func (b *Builder) copyCheck() {
    if b.addr == nil {
        // Первая операция записи: запоминаем собственный физический адрес!
        b.addr = (*Builder)(noescape(unsafe.Pointer(b)))
    } else if b.addr != b {
        // Адрес структуры изменился -> структуру скопировали по значению!
        panic("strings: illegal use of non-zero Builder copied by value")
    }
}
```

```
При первой записи в b1 (по адресу 0x1000):
b1.addr = 0x1000

При копировании b2 := b1 (переменная b2 лежит по адресу 0x2000):
Поле скопировалось как значение: b2.addr = 0x1000!

При попытке записи в b2:
Проверка: b2.addr == &b2 -> 0x1000 == 0x2000 -> ЛОЖЬ!
Вызов panic!
```

> **Железное правило:** `strings.Builder` передается в другие функции **исключительно по указателю: `*strings.Builder`**.

### Метод `.Grow(n)` — Достижение 1 аллокации

Если итоговый размер собираемой строки известен заранее (или его можно оценить):
```go
var sb strings.Builder
sb.Grow(50000 * 11) // Выделили 550 КБ сразу одним куском памяти
```
* **Без `Grow()`:** при росте с нуля буфер будет перевыделять память 15–20 раз в цикле (16 -> 32 -> 64 -> 128...), тратя время на аллокации в куче и копирование старых данных в новый буфер.
* **С `Grow()`:** происходит **ровно 1 аллокация памяти** на старте. Все последующие тысячи вызовов `WriteString` выполняются со скоростью прямой записи процессора в оперативную память.

## 5. Сводное сравнение стратегий сборки строк

| Критерий | Оператор `+` | `bytes.Buffer` | `strings.Builder` | `strings.Builder` + `Grow()` |
| :--- | :--- | :--- | :--- | :--- |
| **Сложность алгоритма** | **O(N^2)** (катастрофа) | O(N) | O(N) | **O(N)** (максимальная скорость) |
| **Аллокации в цикле** | На каждом шаге (N штук) | Геометрический рост (~15 раз) | Геометрический рост (~15 раз) | **0 аллокаций** в цикле |
| **Финальное `.String()`** | Не требуется | **Полное копирование памяти** | **Zero-Copy (0 наносекунд)** | **Zero-Copy (0 наносекунд)** |
| **Суммарно аллокаций** | N штук | ~16 штук | ~16 штук | **Ровно 1 аллокация** |
| **Возможность чтения** | Нет | **Есть** (`ReadRune`, `ReadString`) | Нет (только запись) | Нет (только запись) |
| **Потокобезопасность** | Иммутабельно | Не потокобезопасен | Защищен от копирования | Защищен от копирования |

## 6. Вопросы с собеседований и частые ловушки (FAQ)

### Вопрос 1: Можно ли в `buf.WriteByte` передать число, а не символ?
**Ответ:** Да. `byte` — это алиас для `uint8`. В него можно передать любое целое число от `0` до `255`. Литерал символа `'A'` в Go — это просто синтаксический сахар для константы `65`.

### Вопрос 2: Что делает `buf.WriteRune('🚀')` и как его потом прочитать?
**Ответ:** Руна `'🚀'` — это 4-байтный код Unicode (`U+1F680`). Метод `WriteRune` кодирует его в 4 байта UTF-8 (`[0xF0, 0x9F, 0x9A, 0x80]`) и дописывает их в конец буфера. Чтобы извлечь руну обратно, вызывается `buf.ReadRune()`, который считывает первые биты, распознает длину 4 байта, вычитывает остальные 3 байта, валидирует UTF-8 и склеивает их обратно в одну руну `int32`.

### Вопрос 3: Почему `strings.Builder` работает быстрее `bytes.Buffer` при получении строки?
**Ответ:** `bytes.Buffer.String()` выполняет явное преобразование `string(b.buf[b.off:])`, которое аллоцирует новый блок памяти в куче и копирует байты через `memmove`. `strings.Builder.String()` выполняет Zero-Copy каст через `unsafe.Pointer`, возвращая структуру строки, указывающую непосредственно на байты среза без аллокаций и копирования.

### Вопрос 4: Как `strings.Builder` защищает иммутабельность строки, если мы продолжаем писать после `.String()`?
**Ответ:**
1. Билдер пишет строго в конец (`append-only`), поэтому байты уже отданных строк не перезаписываются.
2. При переполнении емкости `Cap` билдер переезжает в новый массив в куче, а старый массив остается неизменным и удерживается сборщиком мусора, пока на него ссылается строка.
3. При вызове `Reset()` билдер зануляет срез `buf = nil`, а не обрезает `buf[:0]`, исключая перезапись данных старой строки.

### Вопрос 5: Зачем в `strings.Builder` нужно поле `addr *Builder`?
**Ответ:** Это механизм защиты от копирования по значению (`copyCheck`). При первой записи билдер сохраняет в `addr` указатель на себя. Если программист передаст билдер по значению (`b2 := b1`), копия окажется по другому адресу в памяти (`&b2 != b2.addr`), и при следующей операции записи рантайм мгновенно завершит программу паникой, предотвращая взаимное повреждение данных в общем срезе.
