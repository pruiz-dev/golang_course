# Практика 03: Бенчмарк генератора отчетов — strings.Builder против оператора `+`

## Контекст задачи
В реальных высоконагруженных бэкендах генерация отчетов, формирование SQL/JSON-запросов и форматирование логов происходят миллионы раз в сутки.  
Наивное сложение строк через оператор `+` в цикле — одна из главных причин, почему микросервис внезапно начинает «тормозить», жрать гигабайты памяти и нагружать CPU уборкой мусора (Garbage Collection).

Ваша задача — собственными руками написать инструмент замера производительности (Benchmark Runner), сравнить три стратегии конкатенации строк и увидеть колоссальную разницу в скорости.

---

## Техническое задание (Requirements)

Входные данные:
* Количество записей: N = 40 000 (если ваш компьютер очень мощный, можно взять 50 000, но не берите больше 100 000, иначе наивный `+` заблокирует выполнение на десятки секунд!).
* Шаблон одной записи (строка): `"EVENT_LOG: status=200, action=process_payment, code=OK\n"` (длина около 50 байт).

Необходимо реализовать три функции конкатенации:

### 1. `BuildWithPlus(n int, entry string) string`
* Начинает с пустой строки `var s string`.
* В цикле от 0 до N конкатенирует `s += entry`.
* Возвращает итоговую строку.

### 2. `BuildWithBuilder(n int, entry string) string`
* Создает `var sb strings.Builder`.
* В цикле от 0 до N вызывает `sb.WriteString(entry)`.
* Буфер растет динамически сам (по мере необходимости).
* Возвращает `sb.String()`.

### 3. `BuildWithBuilderPrealloc(n int, entry string) string`
* Создает `var sb strings.Builder`.
* **Заранее рассчитывает точный требуемый размер** памяти: n * len(entry).
* Вызывает метод **`sb.Grow(...)`** до начала цикла.
* В цикле от 0 до N вызывает `sb.WriteString(entry)`.
* Возвращает `sb.String()`.

### 4. Функция `main()`
* Замеряет время работы каждой из трех функций с помощью `time.Now()` и `time.Since()`.
* Выводит в консоль красивую сводную таблицу:
  * Метод сборки
  * Итоговый размер полученной строки в байтах
  * Время выполнения в миллисекундах (`ms`) или микросекундах (`µs`)
* Проверяет валидность: выводит `true`, если все три функции вернули одинаковый результат (`s1 == s2 && s2 == s3`).
* Рассчитывает и выводит кратность ускорения: во сколько раз `strings.Builder` с `Grow()` быстрее, чем наивный `+`.

---

## Критерии приемки (Acceptance Criteria)
1. Код компилируется и запускается без ошибок через `go run main.go`.
2. Все три метода корректно генерируют идентичный текст отчета (проверка на равенство строк дает `true`).
3. Замеры времени наглядно показывают:
   * Способ 1 (`+`) выполняется заметно дольше (обычно сотни миллисекунд или секунды).
   * Способ 2 (`strings.Builder`) работает в десятки раз быстрее.
   * Способ 3 (`strings.Builder` + `Grow`) показывает наивысшую скорость за счет отсутствия промежуточных аллокаций.
4. Вывод в консоль аккуратно отформатирован.

## Архитектурные подсказки (High-Level Hints)
* Пакет `"time"`:
  ```go
  start := time.Now()
  // ... выполнение ...
  duration := time.Since(start)
  ```
* Пакет `"strings"` содержит структуру `strings.Builder`.
* Помните, что `strings.Builder` нельзя передавать в функции по значению (только по указателю `*strings.Builder`), хотя в рамках этой практики каждая функция может создавать свой собственный локальный билдер.
