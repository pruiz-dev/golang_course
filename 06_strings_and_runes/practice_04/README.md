# Practice 04: Подстроки, Утечки памяти (Memory Pinning) и strings.Clone

## 1. Контекст задачи

В высоконагруженных бэкендах на Go частой задачей является парсинг огромных данных: гигабайтных логов доступа, дампов баз данных или тяжелых HTTP-ответов от внешних API.

Неопытные разработчики наивно берут подстроку с помощью среза `s[start:end]` и складывают ее в долговременный кэш или очередь сообщений. В результате сервис незаметно начинает пожирать гигабайты оперативной памяти, хотя размер полезных данных в кэше исчисляется килобайтами.

**Цель этой практики:**  
Своими руками воспроизвести классическую утечку памяти (Memory Pinning), замерить расход кучи через `runtime.MemStats`, а затем устранить утечку идиоматичным способом с помощью `strings.Clone`.

---

## 2. Техническое задание

Разработай консольное приложение-лабораторию в `main.go`, которое наглядно демонстрирует феномен Memory Pinning и его лечение.

### Архитектура и компоненты:

#### 1. Генератор тестовых данных:
* Напиши функцию генерации большой строки (например, 10–20 МБ):
  `generateLargeString(sizeMB int) string`
* Внутри строки или в её начале должен содержаться небольшой маркер/токен (например, `"TOKEN_9876543210"` длиной 16 байт).

#### 2. Два способа извлечения токена:
* **`extractTokenNaive(data string) string`**:  
  Извлекает токен с помощью стандартного среза `data[start:end]`.
* **`extractTokenCloned(data string) string`**:  
  Извлекает токен с помощью среза, но разрывает связь с исходным массивом через `strings.Clone(...)` (Go 1.18+).

#### 3. Утилита замера памяти:
* Функция `printMemUsage(label string)`:
  1. Принудительно вызывает `runtime.GC()`, чтобы сборщик мусора очистил всё ненужное.
  2. Считывает статистику через `runtime.ReadMemStats(&m)`.
  3. Выводит текущий объем занятой кучи (`m.Alloc / 1024 / 1024` в МБ или КБ).

#### 4. Сценарий тестирования в `main()`:
1. **Эксперимент №1: Наивный срез (Memory Pinning)**
   * Создаем срез для хранения токенов: `var naiveTokens []string`.
   * В цикле несколько раз (например, 5–10 раз) генерируем большую строку (по 10 МБ каждая).
   * Вызываем `extractTokenNaive` и сохраняем полученный токен в `naiveTokens`.
   * Сама исходная 10-мегабайтная строка больше нигде не используется и должна быть удалена GC.
   * Вызываем `printMemUsage("После наивных срезов")`.
   * *Ожидаемый эффект:* В куче зависнут десятки мегабайт, потому что крошечные токены удерживают гигантские исходные массивы!

2. **Эксперимент №2: Изолированный срез (`strings.Clone`)**
   * Очищаем старые токены (`naiveTokens = nil`) и вызываем `runtime.GC()`.
   * Создаем срез `var clonedTokens []string`.
   * Повторяем ровно тот же цикл, но сохраняем токены через `extractTokenCloned`.
   * Вызываем `printMemUsage("После strings.Clone")`.
   * *Ожидаемый эффект:* Сборщик мусора без проблем удалит все 10-мегабайтные массивы, и занятая память упадет практически до нуля (считанные килобайты)!

---

## 3. Критерии приемки

1. Проект инициализирован как модуль: `go mod init practice_04`.
2. Код компилируется и запускается через `go run main.go`.
3. В консоли наглядно видна колоссальная разница:
   * Наивный срез держит в памяти 50–100 МБ.
   * Вариант с `strings.Clone` оставляет в памяти лишь несколько килобайт.
4. Проверена эквивалентность извлеченных токенов (`tokenNaive == tokenCloned`).
