# Теория: Цена Эвакуации и Pre-allocation

В прошлой практике мы выяснили, что мапа растет (эвакуируется), когда ее вёдра переполняются.

**Но что физически происходит при Эвакуации?**
1. Среда выполнения (Runtime) Go ставит мапу "на паузу".
2. Выделяется новый блок памяти (в 2 раза больше старого).
3. Все старые пары ключ-значение по одной читаются, заново хэшируются (потому что размер массива бакетов изменился) и кладутся в новые вёдра.
4. Старая память помечается как мусор для сборщика (Garbage Collector).

Это **невероятно медленный процесс**. Если ты добавляешь в пустую мапу миллион элементов, она пройдет через **десятки эвакуаций**, каждый раз останавливая твою программу и сжигая процессорное время на перехэширование.

## Решение: Pre-allocation (Предварительное выделение)
Как и в случае со слайсами, встроенная функция `make` для мап умеет принимать второй аргумент — подсказку о вместимости (Capacity Hint).

```go
// Пустая мапа (начнет с малого количества бакетов и будет постоянно эвакуироваться при росте)
badMap := make(map[string]int)

// Мапа, в которой сразу выделено достаточно бакетов для хранения миллиона элементов
goodMap := make(map[string]int, 1000000)
```

**В чем отличие Capacity Hint для Мап от Capacity для Слайсов?**
* В слайсах `make([]int, 0, 10)` создает жесткий массив на 10 элементов.
* В мапах `make(map[int]int, 1000)` — это лишь подсказка (`hint`) для среды выполнения: *"Эй, скоро сюда прилетит тысяча элементов. Выдели сразу столько бакетов, чтобы мне не пришлось эвакуироваться"*.
* При этом длина (`len`) у мапы по-прежнему будет равна `0`. Никакие "пустые" ключи в ней не создаются.

Правило: **Если ты знаешь примерное количество элементов, которые попадут в мапу — всегда передавай эту цифру в `make`. Это может ускорить твой код в несколько раз.**
